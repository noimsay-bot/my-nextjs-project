# review-loop

이 루프는 사람이 매번 잔소리하지 않아도 Codex가 반복 수행해야 하는 기본 절차다.

## 기본 루프
1. 작업 전 [../../AGENTS.md](../../AGENTS.md)를 읽는다.
2. 관련 [../README.md](../README.md)와 도메인 문서를 읽는다.
3. 관련 에이전트를 호출하거나 셀프 리뷰한다.
4. 구현 범위를 최소화해 수정한다.
5. `npm run harness:all`을 실행한다.
6. `npm run lint`, `npm run test:regression`, 가능하면 `npm run build`를 실행한다. 브라우저 검증은 `npm run test:e2e:offline`을 우선한다. 운영 인증을 사용하는 기존 `npm run test:e2e`는 별도 테스트 환경을 확인한 뒤 실행한다.
7. 에이전트별 리뷰를 다시 수행한다.
8. 피드백을 가능한 범위에서 반영한다.
9. 재검증한다.
10. 최종 보고서에 변경 파일, 이유, 영향, 명령, 결과, 배포 전 확인사항을 쓴다.

## 실패 처리
- 하네스 스크립트 실패는 먼저 수정한다.
- lint/build 실패는 이번 변경 때문인지 기존 문제인지 구분한다.
- 서비스 대규모 리팩터링이 필요하면 임의로 확대하지 않고 보고한다.

## 운영 연결 없는 검증

- `test:regression`: Node 테스트 러너로 실제 저장 모듈을 테스트 대역에 연결한다. SQL은 메모리 내 PostgreSQL 엔진에 합성 사용자/테이블을 만들어 권한 및 롤백을 검사한다.
- `test:e2e:offline`: `.env*`를 제외한 소스를 임시 디렉터리에 복사하고 가짜 Supabase 설정으로 Next를 시작한다. 서버는 비로컬 소켓 연결을 차단하고 브라우저는 명시적으로 허용된 로컬 페이지와 합성 응답만 사용한다.
- 테스트 전용 컴포넌트 페이지는 임시 복사본에만 추가한다. 배포 앱에는 테스트 경로나 인증 우회를 추가하지 않는다.
- `npm run harness:all`을 두 번 실행해 generated 문서 내용이 동일해야 한다. `harness:docs`는 생성물을 수정하지 않고 현재 코드에서 생성될 내용과 비교한다.
- 로컬 SQL 테스트는 운영의 실제 정책/스키마 및 여러 DB 연결 사이의 동시성을 증명하지 않는다. SQL 배포 전 별도 검증은 [안정화 실행 기록](../exec-plans/stabilization-2026-09.md)을 따른다.
